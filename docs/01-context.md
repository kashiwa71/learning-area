# コンテキストという制約

エージェントが一度に見ていられる文章の量には上限がある。この領域を**コンテキストウィンドウ**と呼び、
そこには会話のすべてが載る。開発者が打った指示、エージェントの返答、読んだファイルの中身、
実行したコマンドの出力。調査を一度させれば数万トークンが積まれることも珍しくない。

厄介なのは、上限に達したときに止まるのではなく、埋まるにつれて性能がなだらかに落ちることである。
序盤に出した指示が効かなくなり、同じ誤りを繰り返し、すでに読んだファイルをまた読む。
「さっき言ったのに」という状況の多くは、モデルの能力ではなく、この目減りで説明がつく。

以降の教材に出てくる作法は、ほぼすべてこの一点から導かれる。`CLAUDE.md` を短く保つのも、
手順をスキルに分けるのも、調査をサブエージェントに投げるのも、常駐させる文章を減らすための手段である。

## 何がいつ読み込まれるか

置き場所によって、読み込まれる時点が違う。毎回載るものは常に予算を食い、呼ばれたときに載るものは
使わない限りほぼ無料である。

| 置き場所 | 読み込まれる時点 |
|---------|-----------------|
| `CLAUDE.md`（作業ディレクトリと、その上位） | セッション開始時 |
| `.claude/rules/*.md`（`paths` 指定なし） | セッション開始時 |
| `.claude/rules/*.md`（`paths` 指定あり） | 一致するファイルを読んだとき |
| サブディレクトリの `CLAUDE.md` | そのディレクトリのファイルを読んだとき |
| スキルの `description` | セッション開始時（一覧として） |
| スキルの本文 | 呼び出されたとき |
| サブエージェントが読んだファイル | 本体には載らない（結果の要約だけ返る） |

`CLAUDE.md` に長い手順書を書くと、その手順を使わないセッションでも毎回代金を払うことになる。
同じ内容をスキルに移せば、`description` の一行だけが常駐し、本文は呼ばれたときに読み込まれる。
この置き換えが、設定を整理するときの最も効く操作である。

読み込まれた結果は `/context` で確認できる。書いたのに効いていないと感じたら、まずここで実際に
読まれているかを見る。読まれていなければ、置き場所の問題であって、書き方の問題ではない。

## 溜まった文脈を捨てる

長いセッションほど良い結果が出るわけではない。無関係な情報が溜まるほど判断は鈍る。
捨てる手段はいくつかあり、捨てる量で使い分ける。

- `/clear`：会話をすべて破棄する。別の作業に移るときに使う。
- `/compact <指示>`：会話を要約に畳む。`/compact API の変更点を残して` のように何を残すか指定できる。
- `Esc` 二回、または `/rewind`：特定の時点まで会話とファイルの状態を巻き戻す。
- `/btw`：会話履歴に残さずに質問する。ついでの確認で文脈を太らせずに済む。

同じ誤りを二回訂正したら、`/clear` して指示を書き直したほうが速い。訂正が積まれた文脈には
失敗した方針がそのまま残っていて、エージェントはそれを読み続ける。学んだことを織り込んだ新しい指示を
一度で出すほうが、汚れた文脈で三回訂正するより結果が良い。

## 調査を別の場所でやらせる

コードベースの調査は、性質上たくさんのファイルを読む。読んだ内容の大半は結論が出れば不要になるが、
本体のセッションで読ませると全部が残る。

サブエージェントは独立したコンテキストウィンドウで動き、本体には結果だけを返す。
「認証まわりでトークン更新をどう扱っているか調べて」のような調査は、サブエージェントに投げると
本体の文脈をほとんど消費しない。詳しくは[サブエージェント](05-subagents.md)で扱う。

## 予算の配分として考える

常駐させる文章は、開発者が意図的に選んだものだけにする。判断の基準は一つで、
「これが無いとエージェントが誤るか」を各行に問う。誤らないなら消す。
たまにしか要らないなら、スキルかパススコープ付きルールに移す。

この配分を最初に決めておくと、[CLAUDE.md の書き方](02-claude-md.md)で出てくる
「200行以内に収める」という目安が、根拠のある制約として読めるようになる。
