# 仕事の進め方

設定ファイルを整えても、依頼の出し方が雑なら結果は良くならない。ここでは、一つの作業を
どういう順で進めるかを扱う。

## 検証手段を先に用意する

エージェントは、仕事が終わったように見えた時点で止まる。合否を返すものが無ければ、
「終わったように見える」以外の判断材料が無いからで、以降の誤りは開発者が気付くまで残る。

合否を返すものは何でもよい。テスト、ビルドの終了コード、リンタ、出力を期待値と比較するスクリプト、
画面のスクリーンショット。これがあれば、エージェントは自分で結果を読んで直し、通るまで繰り返す。
任せられる仕事の大きさは、ほぼこの一点で決まる。

| やり方 | 依頼の形 |
|--------|---------|
| 判定基準を渡す | 「`validateEmail` を書いて。`user@example.com` は true、`invalid` は false、`user@.com` は false。実装後にテストを走らせて」 |
| 画面で確かめさせる | 「この設計どおりに実装して。結果のスクリーンショットを撮って元と比べ、違いを挙げて直して」 |
| 症状から入らせる | 「ビルドがこのエラーで失敗する（貼り付け）。原因を直してビルドが通ることを確認して。エラーの抑制ではなく原因の除去で」 |

やったと言わせるのではなく、証拠を出させる。テストの出力、実行したコマンドとその戻り値、
結果の画像。証拠を読むほうが、自分で検証をやり直すより速い。

より強く縛りたいときは、`Stop` フックにテストを仕込んで、通るまでターンを終わらせない構成にできる。
詳しくは[フック](06-hooks.md)にある。

## 調査、計画、実装、コミット

いきなり実装させると、間違った問題を正しく解くことがある。プランモードを使うと、
調べる段階と書き換える段階を分けられる。

1. **調査**：`Shift+Tab` を押してプランモードに入る（`⏸ plan mode on` と出る）。
   ファイルを読ませ、質問に答えさせる。この間、ソースは書き換えられない。
2. **計画**：「Google OAuth を足したい。どのファイルが変わる。セッションの流れは。計画を書いて」と依頼する。
   `Ctrl+G` で計画をエディタに開き、自分で直せる。
3. **実装**：計画を承認するか `Shift+Tab` でモードを抜け、計画に沿って書かせる。
4. **コミット**：「説明的なメッセージでコミットして、PR を作って」

プランモードには手間がかかる。誤字の修正、ログの追加、変数名の変更のように、
差分を一文で説明できる作業なら、そのまま頼めばよい。効くのは、方針に迷いがあるとき、
複数のファイルにまたがるとき、触る場所に馴染みが無いときである。

## 指示を具体的にする

エージェントは意図を推測するが、読心はしない。ファイル名、条件、参考にすべき既存のパターンを挙げる。

| 直し方 | 前 | 後 |
|--------|-----|-----|
| 範囲を絞る | 「foo.py のテストを書いて」 | 「foo.py の、ログアウト済みの場合の edge case のテストを書いて。モックは使わないで」 |
| 情報源を指す | 「なぜこの API はこんな形なの」 | 「ExecutionFactory の git 履歴を追って、この API がどう出来上がったか要約して」 |
| 既存の型を示す | 「カレンダーを足して」 | 「ホーム画面のウィジェットの実装を読んで、その形に合わせてカレンダーを作って。HotDogWidget.php が参考になる。既存の依存以外は増やさないで」 |
| 症状で言う | 「ログインのバグを直して」 | 「セッション期限切れ後にログインが失敗する。src/auth/ のトークン更新を見て。再現する失敗テストを書いてから直して」 |

`@` でファイルを指せば、説明せずに読ませられる。画像は貼り付けられる。
`cat error.log | claude` でログを直接流し込むこともできる。

探索の段階では、曖昧なままのほうがよいこともある。「このファイルで直したほうがいい点は」と聞くと、
自分では思い付かなかった指摘が出てくる。

## 仕様を先に引き出す

大きめの機能では、実装より先に仕様を固めたほうが結果が良い。自分で仕様書を書く代わりに、
エージェントに質問させる手がある。

```text
[機能の一行説明] を作りたい。AskUserQuestion ツールで詳しく聞き取りをして。

技術的な実装、UI、edge case、懸念、trade-off について聞いて。
分かりきったことは聞かず、私が考えていない難しいところを掘り当てて。

全部聞き尽くしたら、完全な仕様を SPEC.md に書いて。
```

聞かれて初めて気付く論点が出てくる。仕様が固まったら、`/clear` するか新しいセッションを開いて、
そこで実装に入る。実装のセッションには聞き取りの経緯が残らず、文脈が仕様書だけになる。

良い仕様書は、それ単体で読める。関係するファイルとインタフェースの名前が書いてあり、
何を範囲外とするかが書いてあり、最後に「これが通れば完成」と言える検証手順で終わっている。
雛形が [templates/SPEC.md](../templates/SPEC.md) にある。

## 途中で直す

うまくいっていないと感じたら、早い段階で止める。

- `Esc`：作業中のエージェントを止める。文脈は残るので、そのまま方向を変えられる。
- `Esc` 二回、または `/rewind`：会話とファイルの状態を、選んだ時点まで戻す。
- 「さっきの変更を取り消して」：エージェント自身に戻させる。
- `/clear`：文脈を捨てて仕切り直す。

同じ点を二回訂正したら、`/clear` して指示を書き直す。訂正が積まれた文脈には失敗した方針が残っていて、
エージェントはそれを読み続ける。学んだことを織り込んだ新しい指示を一度で出すほうが、
汚れた文脈で三回訂正するより速い。

なお、`/rewind` が戻せるのはエージェントのファイル編集ツールが行った変更だけである。
シェル経由の変更や外部プロセスの副作用は戻らない。git の代わりにはならない。

## 書いた本人以外に検証させる

無人で走る時間が長いほど、独立した点検の価値が上がる。差分だけを見るサブエージェントは、
その差分を生んだ推論を知らないので、推論に納得したまま見落とす、ということが起きにくい。

正しさの確認だけなら同梱の `/code-review` が使える。自分の書いた計画と突き合わせたいときは、
依頼文を自分で書く。詳しくは[サブエージェント](05-subagents.md)にある。

## 並行して走らせる

一つのセッションで満足に進められるようになったら、数を増やせる。

- **worktree**：独立した git のチェックアウトで別セッションを動かし、編集の衝突を避ける
- **非対話モード**：`claude -p "..."` をスクリプトから呼ぶ。CI や pre-commit に組み込める
- **書き手と読み手**：一方に実装させ、もう一方の新しい文脈でレビューさせる

大量のファイルに同じ変更を入れるなら、対象の一覧を作らせてからループで回す。

```bash
for file in $(cat files.txt); do
  claude -p "$file を Python 2 から 3 へ移行して。OK か FAIL だけ返して" \
    --allowedTools "Edit,Bash(git commit *)"
done
```

最初の 2〜3 ファイルで指示を調整してから全体に流す。無人で走らせるときは
`--allowedTools` で権限を絞る。
