# サブエージェント

調査は、性質上たくさんのファイルを読む。読んだ内容の大半は結論が出れば要らなくなるが、
本体のセッションで読ませると全部がコンテキストに残る。「認証まわりを調べて」の一言で
数十ファイルが積まれ、その後の実装の判断が鈍る。

**サブエージェント**は、独立したコンテキストウィンドウで動く別のエージェントである。
自分の窓でファイルを読み、結果の要約だけを本体に返す。読んだ中身は本体に載らないので、
調査の代金を実装のための領域から切り離せる。

## 定義の書き方

`.claude/agents/` に Markdown ファイルを置く。フロントマターで性格と権限を決め、本文がそのエージェントへの指示になる。

```markdown
---
name: code-reviewer
description: コード品質、セキュリティ、保守性の観点でレビューする。変更を書き終えた直後に使う。
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたは上級のコードレビュアーである。呼ばれたら次の順で進める。

1. `git diff` で最近の変更を確認する
2. 明確さ、セキュリティ、性能の観点で読む
3. 優先度順に、実行可能な指摘を返す

重大な問題を先に、次に警告、最後に提案を挙げる。
```

| 場所 | 効く範囲 |
|------|---------|
| `~/.claude/agents/` | 自分の全プロジェクト |
| `.claude/agents/` | そのプロジェクト（git に入れてチームで共有する） |

## フロントマターの項目

`name` と `description` だけが必須である。`description` は、エージェントがどの仕事を誰に任せるかを
判断する材料になるので、担当範囲を具体的に書く。

| 項目 | 用途 |
|------|------|
| `name` | 識別子。英小文字とハイフンのみ |
| `description` | いつ委譲するか |
| `tools` | 使わせるツールの許可リスト。省略すると全部 |
| `disallowedTools` | 使わせないツール。`tools` より先に適用される |
| `model` | `sonnet`、`opus`、`haiku`、`inherit` |
| `permissionMode` | `default`、`acceptEdits`、`auto`、`plan`、`bypassPermissions` |
| `skills` | 起動時に読み込ませるスキル |
| `memory` | 記憶の保存範囲。`user`、`project`、`local` |
| `maxTurns` | 打ち切るまでのターン数の上限 |
| `isolation` | `worktree` にすると独立した git worktree で動く |

説明文は全エージェント分が常駐するので、短く書く。合計が長くなると警告が出る。

レビュー役や調査役には `tools` を読み取り系だけに絞る。上の例には `Edit` も `Write` も無いので、
このエージェントは指摘を返すことしかできない。レビューのついでに勝手に直される事故を、
指示ではなく構成で防げる。

## 何を引き継ぎ、何を引き継がないか

サブエージェントは毎回まっさらな状態から始まる。

引き継ぐもの：本文に書いたシステムプロンプト、`CLAUDE.md`、git の状態、`skills` で指定したスキル、
そして呼び出し元が渡したタスクの説明。

引き継がないもの：それまでの会話、出力スタイルの設定、本体が溜めた記憶。

だから、呼び出すときの依頼文にすべての前提を書く必要がある。「さっきの件で」は通じない。
これは制約であると同時に利点でもある。会話の流れを知らない相手のほうが、
自分が書いたコードに引きずられずに評価できる。

## 呼び出し方

依頼文で名指しする方法が普通である。

```text
code-reviewer サブエージェントで、直近の変更をレビューして
```

確実に起動させたいときは `@"code-reviewer (agent)"` と書く。セッション全体をそのエージェントとして
動かすなら `claude --agent code-reviewer` で起動する。

## 効く二つの使い方

**調査を逃がす**。実装に入る前の下調べは、サブエージェントに投げると本体が汚れない。

```text
サブエージェントで、認証まわりがトークン更新をどう扱っているか、
再利用できる OAuth のユーティリティが既にあるかを調べて
```

**書いた本人以外に検証させる**。実装を終えたら、差分だけを見る相手に点検させる。
書いた経緯を知らないので、その経緯に納得したまま見落とす、ということが起きにくい。

```text
サブエージェントで、レート制限の差分を PLAN.md と突き合わせて。
要件がすべて実装されているか、挙げた edge case にテストがあるか、
範囲外の変更が混じっていないかを見て。指摘は正しさに関わるものだけにして。
```

最後の一文を落とさないほうがよい。指摘を探せと言われたレビュアーは、
問題が無くても何かを指摘する。全部に対応すると、要らない抽象化と防御的なコードが増える。
正しさか要件に関わるものだけを挙げさせ、残りは任意扱いにする。

差分の正しさを見るだけなら、同梱の `/code-review` が同じことをする。
自分で書いた計画と突き合わせたいときに、依頼文を自分で書く価値が出る。
