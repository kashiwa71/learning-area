# ルールの分割

プロジェクトが育つと `CLAUDE.md` に規約が集まり、200行の目安をすぐ超える。
`.claude/rules/` は、その中身を話題ごとのファイルに分けて置くための場所である。

分けるだけなら見通しが良くなるだけだが、`paths` を指定すると読み込まれる時点が変わる。
一致するファイルをエージェントが読んだときにだけ載るので、常駐する文章を増やさずに規約を増やせる。

## 置き方

`.claude/rules/` に `.md` ファイルを置く。サブディレクトリも再帰的に探索されるので、
`frontend/`、`backend/` のように分けてよい。

```text
your-project/
├── CLAUDE.md
└── .claude/
    └── rules/
        ├── code-style.md
        ├── testing.md
        └── api/
            └── error-format.md
```

`paths` の無いファイルは、`.claude/CLAUDE.md` と同じ扱いで起動時に読み込まれる。
つまり、単に分割しただけではコンテキストの消費量は変わらない。

## パスで絞る

YAML フロントマターに `paths` を書くと、一致するファイルを扱うときだけ読み込まれる。

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API の規約

- エンドポイントは必ず入力検証を通す
- エラー応答は `{ error: { code, message } }` の形に揃える
- 一覧を返すエンドポイントはページネーションを付ける
```

複数のパターンを並べられ、波括弧での展開も使える。

```markdown
---
paths:
  - "src/**/*.{ts,tsx}"
  - "tests/**/*.test.ts"
---
```

| パターン | 一致するもの |
|---------|-------------|
| `**/*.ts` | すべてのディレクトリの TypeScript ファイル |
| `src/**/*` | `src/` 以下のすべて |
| `*.md` | リポジトリ直下の Markdown |
| `src/components/*.tsx` | そのディレクトリ直下のコンポーネント |

`[` はブラケット式の開始として解釈されるため、ファイル名に含めたい場合は `photos \[2024/**` のように
バックスラッシュで escape する。

## 個人のルール

`~/.claude/rules/` に置いたものは、そのマシンの全プロジェクトに効く。エディタの好みや、
どのプロジェクトでも変わらない自分の作法はここに置く。プロジェクトのルールより先に読み込まれるので、
競合したときはプロジェクト側が優先される。

複数のプロジェクトで同じルールを共有したいなら、シンボリックリンクが使える。

```bash
ln -s ~/company-standards/security.md .claude/rules/security.md
```

## 何をどこに置くか

ここまでに出た置き場所を、内容の性質で整理すると次のようになる。判断に迷ったら、
「毎回要るか」と「例外を許さないか」の二つを問う。

| 内容の性質 | 置き場所 |
|-----------|---------|
| 毎回必要な事実（コマンド、全体の規約） | `CLAUDE.md` |
| 特定の種類のファイルにだけ効く規約 | `.claude/rules/`（`paths` 付き） |
| たまに使う手順、複数ステップの作業 | `.claude/skills/` |
| 例外なく実行されなければ困ること | [フック](06-hooks.md) |
| 読ませない、書かせない | [権限ルール](07-permissions.md)の `deny` |

ルールとスキルの境目が紛らわしい。ルールは「こういうファイルを触るときはこう書く」という常時の規約で、
エージェントが呼び出すものではない。スキルは「この作業をするときはこの手順で」という呼び出される単位である。
判断がつかないときは、その文章が命令形の手順で書けるかを見る。書けるならスキルにする。
