# エージェントコーディングとは何か

エディタの補完は、開発者が書きかけたコードの続きを提案する。採用するか捨てるかを決めるのは開発者で、
判断の主体は動いていない。提案が的外れなら無視すればよく、それで作業は止まらない。

コーディングエージェントはここが違う。指示を受けたエージェントは、関係のありそうなファイルを自分で探して読み、
コードを書き換え、テストを走らせ、失敗の出力を読み、原因を推測してまた書き換える。開発者が次の入力をするまでの間に、
判断と実行が何度も挟まる。**エージェントコーディング**と呼んでいるのは、この、結果を読んで自分で次の手を決めるループに
仕事を預ける進め方を指す。

## ループが回る条件

エージェントが自力で進めるのは、次の手を決める材料が手元にある間だけである。材料は二種類ある。

- **文脈**：このプロジェクトで何が正しいのかを示す情報。ビルドコマンド、命名規約、置き場所の決まり、過去の設計判断。
- **検証手段**：やったことが正しかったかを機械が答えてくれる仕組み。テスト、型検査、リンタ、ビルドの終了コード。

検証手段が無いと、エージェントは「できたように見える」ところで止まる。それ以上の判断材料が無いからで、
以降の誤りはすべて開発者が気付くまで残る。逆にテストが一つあれば、エージェントは失敗を読んで直し、
通るまで自分で繰り返せる。任せられる仕事の大きさは、この検証手段の有無でほぼ決まる。

文脈のほうは、放っておくとエージェントがコードを読んで推測する。推測できるものは書かなくてよい。
問題になるのは、コードを読んでも分からないもの（環境変数の要否、なぜこの実装を選んだか、どのコマンドを叩けばよいか）で、
これを毎回チャットで説明し直しているうちは、任せられる範囲が広がらない。

## 指示が効く三つの層

同じ「こうしてほしい」を伝えるにも、書く場所によって効き方が変わる。効く範囲と強さが違うので、
内容に応じて置き場所を選ぶことになる。

| 層 | 置き場所 | 効く範囲 | 強さ |
|----|---------|---------|------|
| 会話 | その場のプロンプト | そのセッションだけ | 直後は強いが、文脈が伸びると薄れる |
| リポジトリの設定 | `CLAUDE.md`、`.claude/rules/`、`.claude/skills/` | セッションをまたいで毎回 | 従う努力はするが、保証は無い |
| 機構 | フック、権限ルール | 毎回、モデルの判断と無関係に | 実行される、あるいは実行されない |

`CLAUDE.md` に書いた規約は、エージェントに渡される文章であって、設定ではない。読んだうえで従おうとするが、
指示が曖昧だったり、他の指示と矛盾していたり、量が多すぎたりすると埋もれる。
「コミット前に必ずリントを通す」のように、例外なく実行されなければ困ることは、フックに移す。
「このパスは絶対に触らせない」であれば権限ルールになる。この三層の使い分けが、設定を書くときの中心的な判断になる。

## 何を任せ、何を任せないか

任せやすいのは、正しさの判定が機械にできる仕事である。テストのあるリファクタリング、型エラーの解消、
既存パターンに沿った実装の追加、失敗しているテストの原因調査。どれも合否がその場で出る。

任せにくいのは、何が正しいかを人間しか知らない仕事である。要件のどれを優先するか、既存の設計を壊してでも
作り直すべきか、この API を外部に公開してよいか。エージェントは尤もらしい選択をするが、
尤もらしさと正しさが一致する保証は無い。こうした判断は、実装を始める前に開発者が決めて、
決めた内容を文章として渡す。[仕様を先に固める進め方](08-workflow.md#仕様を先に引き出す)がここに効く。
