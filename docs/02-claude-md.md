# CLAUDE.md の書き方

`CLAUDE.md` は、セッションが始まるたびにエージェントへ渡される文章である。プロジェクトの決まりごとを
そこに書いておけば、毎回チャットで説明し直さずに済む。

はじめに一つ区別しておく。これは設定ファイルではなく、指示文である。エージェントは読んだうえで従おうとするが、
権限ルールやフックのように機構として強制されるわけではない。例外なく実行されなければ困ることは、
[フック](06-hooks.md)に移す必要がある。この違いを踏まえないまま「書いたのに守らない」と悩むことになりやすい。

## 置き場所

読み込まれる順に並べると次のようになる。後に読まれるものほど、エージェントの直前の記憶に近い位置に入る。

| 範囲 | 場所 | 用途 |
|------|------|------|
| 組織 | `/etc/claude-code/CLAUDE.md`（Linux、WSL）<br>`/Library/Application Support/ClaudeCode/CLAUDE.md`（macOS） | 全社の規約。管理者が配布する |
| 個人 | `~/.claude/CLAUDE.md` | 自分の全プロジェクトに効く好み |
| プロジェクト | `./CLAUDE.md` または `./.claude/CLAUDE.md` | チームで共有する規約。git に入れる |
| 個人かつプロジェクト | `./CLAUDE.local.md` | 自分だけの設定。`.gitignore` に入れる |

作業ディレクトリと、その上位ディレクトリにある `CLAUDE.md` は起動時に読み込まれる。
サブディレクトリに置いたものは、エージェントがそのディレクトリのファイルを読んだ時点で読み込まれる。
モノレポでパッケージごとに規約が違うなら、この性質を使ってパッケージ直下に置くとよい。

見つかったファイルは互いを上書きせず、すべて連結される。矛盾する指示が別々のファイルにあると、
どちらかが恣意的に選ばれる。定期的に読み返して、古くなった記述を消す作業が要る。

## 何を書き、何を書かないか

`CLAUDE.md` は毎回読み込まれるので、行数がそのまま常駐コストになる。各行に
「これが無いとエージェントは誤るか」と問い、誤らないなら消す。

| 書く | 書かない |
|------|---------|
| 推測できないコマンド（`make dev-setup` など） | コードを読めば分かること |
| 既定と違うコード規約 | 言語の標準的な作法 |
| テストの走らせ方、使うテストランナー | API の詳細な仕様（リンクで足りる） |
| ブランチ名やコミットの慣習 | 頻繁に変わる情報 |
| このプロジェクト固有の設計判断 | 長い解説やチュートリアル |
| 環境の癖（必要な環境変数、ローカルの前提） | ファイルごとの説明 |
| 非自明な落とし穴 | 「読みやすいコードを書く」のような一般論 |

ディレクトリ構成の一覧や依存パッケージの列挙は、エージェントが自分で調べられるので載せる必要がない。
`/doctor` を実行すると、こうした削れる記述の候補を提案してくれる。

## 具体的に書く

同じ内容でも、検証できる形で書いたほうが従われやすい。

```markdown
# 悪い例
- コードを適切にフォーマットすること
- 変更したらテストすること
- ファイルは整理して置くこと

# 良い例
- インデントは半角スペース2つ
- コミット前に `npm run lint && npm test` を通す
- API のハンドラは `src/api/handlers/` に置く
```

左の三行は、何をすれば満たしたことになるのかが決まらない。右の三行は決まる。
エージェントが従ったかどうかを開発者が判定できない指示は、エージェントにとっても従いようがない。

一行だけどうしても守らせたいものがあれば、その行に `IMPORTANT:` を付ける。ただし複数の行を強調すると
どれも目立たなくなるので、一つのファイルに一箇所か二箇所までにする。

## 分量

200行を目安にする。長くなるほど個々の指示の追従率が落ちるためで、
守ってほしい規約を足したのに全体としては守られなくなる、という逆転が起きる。

超えそうなときの逃がし先は二つある。特定の種類のファイルにだけ効く規約なら
[パススコープ付きルール](03-rules.md)へ、手順として書いてあるものなら[スキル](04-skills.md)へ移す。
どちらも、必要になった時点で読み込まれる。

## 他のファイルを取り込む

`@path/to/file` と書くと、そのファイルの内容が展開されて読み込まれる。

```markdown
プロジェクトの概要は @README.md を参照。

# 追加の指示
- git の運用 @docs/git-instructions.md
```

相対パスは、書いてあるファイルからの相対で解決される。取り込んだ先がさらに取り込むこともでき、
4段までたどる。バッククォートで囲めば取り込まれず、ただの文字列として扱われる。

取り込みは整理の手段であって、削減の手段ではない。展開された内容は起動時にすべて読み込まれるので、
コンテキストの消費量は分割前と変わらない。

## AGENTS.md がすでにある場合

Claude Code が読むのは `CLAUDE.md` であって `AGENTS.md` ではない。他のエージェント向けに
`AGENTS.md` を運用しているなら、内容を二重管理せずに済ませる書き方がある。

```markdown
@AGENTS.md

## Claude Code

`src/billing/` を変更するときはプランモードを使う。
```

取り込みが先に展開され、その下に Claude Code 固有の指示が続く。Claude Code 固有の追記が不要なら、
`ln -s AGENTS.md CLAUDE.md` でシンボリックリンクを張ってもよい（Windows では管理者権限が要るため、
取り込みのほうが無難である）。

## 最初の一枚を作る

`/init` を実行すると、コードベースを調べてビルドコマンドやテスト手順を含む `CLAUDE.md` の草案を作る。
すでにファイルがある場合は、上書きせずに改善案を出す。

自動生成された内容は、エージェントがコードから読み取れたものなので、そのままだと
「書かなくてよいこと」が多く含まれる。生成後に一度削る作業を挟んで、コードを読んでも分からない情報
（なぜこの構成なのか、何を叩けばよいのか、どこを触ると壊れるか）を手で足す。

## 育て方

最初から完成させようとせず、必要が生じた時点で足す。追記する合図は決まっている。

- 同じ誤りを二度目にされたとき
- レビューで、エージェントが知っていれば防げた指摘を受けたとき
- 前のセッションと同じ訂正をチャットに打ったとき
- 新しく入った人に同じ説明をしたとき

足すだけでは肥大するので、削る機会も要る。書いた規約をエージェントが指示なしでも守るようになっていれば、
その行は消してよい。手順として書いた段落が数行を超えたら、スキルに移す時期にきている。

このリポジトリには、この刈り込みを対話で進めるスキルを置いてある。
`/claude-md-review` で起動する（実装は [.claude/skills/claude-md-review/SKILL.md](../.claude/skills/claude-md-review/SKILL.md)）。

## 効いていないときの診断

守られない原因は、たいてい次のどれかに当たる。上から順に確認する。

1. **読み込まれていない**：`/context` を実行して、Memory files の一覧に出ているか見る。無ければ置き場所が違う。
2. **曖昧**：判定できない書き方になっている。検証できる文に直す。
3. **矛盾**：上位ディレクトリや `.claude/rules/` に反対のことが書いてある。両方を読み直す。
4. **埋もれている**：ファイルが長すぎる。削るか、スキルとルールに分ける。
5. **そもそも指示で足りない**：例外を許さない要求なら、[フック](06-hooks.md)にする。

なお `<!-- コメント -->` は読み込み時に取り除かれる。人間の保守者向けの覚書は、コンテキストを消費せずに書ける。
