# 新規プロジェクトの立ち上げ

既存のコードベースなら `/init` を叩けば、エージェントがコードを読んで `CLAUDE.md` の草案を作る。
新規プロジェクトではこれが使えない。読むコードがまだ無く、規約も決まっていないからで、
最初の一枚は手で書くことになる。

とはいえ、最初から完全な設定を用意する必要はない。整備には順序があり、
先にやったほうが効くものから並べると、以下のようになる。

## 整備の順序

| 段階 | やること | なぜその順か |
|------|---------|-------------|
| 1 | 検証手段を用意する | これが無いと、以降の設定を足しても任せられる範囲が広がらない |
| 2 | 権限を許可する | 検証コマンドを毎回承認していると、ループが人間待ちで止まる |
| 3 | `CLAUDE.md` を書く | 上の二つが揃って初めて、規約を書く意味が出る |
| 4 | スキルとルールに分ける | `CLAUDE.md` が育ってきた時点で移す |
| 5 | フックで固定する | 守られないことが実際に起きた規約だけを移す |
| 6 | サブエージェントを足す | 調査とレビューの頻度が上がってきたら |

飛ばして 5 から始めると、まだ起きていない問題への対策を書くことになる。
順に足していくほうが、結果として書く量が少なくて済む。

## 最初の三十分

### 検証手段を先に作る

コードを一行も書いていない段階でも、失敗するテストは書ける。あるいは
「何もしないが正常終了する」ビルドスクリプトを置くだけでもよい。

```bash
mkdir my-project && cd my-project && git init
# 言語に応じた初期化（npm init、cargo new、uv init など）
# テストを一つ書き、落ちることを確認する
```

大事なのは、`npm test` に相当する一つのコマンドが存在して、
成功と失敗を終了コードで返すことである。エージェントに渡せる合否がここで生まれる。

### 権限を許可する

`.claude/settings.json` を作り、繰り返し走らせるコマンドを通しておく。

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(npm test *)",
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(git push --force *)"
    ]
  }
}
```

`git push` を許可に入れるかは好みが分かれる。慣れるまでは外しておき、
PR を作る操作だけ都度承認するほうが落ち着いて進められる。

### CLAUDE.md を書く

最初の一枚は短くてよい。コードを読んでも分からないことだけを書く。

```markdown
# my-project

社内の請求データを取り込んで月次レポートを出すバッチ。Node.js で書く。

## コマンド

- `npm run dev`：ローカル実行。`.env` に `DB_URL` が必要
- `npm test`：単体テスト
- `npm run lint`：ESLint と Prettier の検査

## 決めごと

- 変更を終えたら `npm run lint && npm test` を通す
- 外部 API の呼び出しは `src/clients/` に閉じる。他の層から直接叩かない
- 日付は UTC で保持し、表示のときだけ JST に変換する

## git

作業ブランチを切る。main に直接コミットしない。
```

十数行で足りる。この時点で書けるのは、コマンドと、自分がすでに決めている方針だけである。
規約は書いてから守らせるのではなく、破られたときに書き足す。

## 最初の一週間

コードが増えてきたら `/init` を実行する。今度は読むコードがあるので、
気付いていなかったコマンドや構成を拾ってくれる。生成された内容には
「コードを読めば分かること」が混ざるので、採用する前に削る。

規約を足す合図は決まっている。

- 同じ誤りを二度目にされた
- レビューで、エージェントが知っていれば防げた指摘を受けた
- 前のセッションと同じ訂正をチャットに打った

この三つのどれかが起きたときだけ足す。予防的に書いた規約は、たいてい使われないまま常駐する。

同じ手順を三回チャットに貼り付けたら、[スキル](04-skills.md)にする。
規約が特定の種類のファイルにしか効かないと気付いたら、[パススコープ付きルール](03-rules.md)に移す。
`CLAUDE.md` が 200 行に近付いてきたら、どちらかへの移動が遅れている。

## 定着してきたら

`CLAUDE.md` に書いたのに守られない規約が出てくる。整形、リント、テストのように
機械で判定できるものは[フック](06-hooks.md)に移す。移せたら `CLAUDE.md` からその行を消す。
機構が保証するようになったものを、指示としても持ち続ける必要は無い。

調査とレビューの頻度が上がってきたら、[サブエージェント](05-subagents.md)を用意する。
読み取り専用のレビュアーを一つ置いておくと、実装のたびに独立した点検を挟める。

`.claude/settings.local.json` に溜まった許可のうち、チーム全員に共有してよいものを
`.claude/settings.json` へ移す。個人の環境依存のものは残す。

## 立ち上げの点検表

- [ ] 一つのコマンドでテストが走り、終了コードで合否が分かる
- [ ] そのコマンドが `.claude/settings.json` の `allow` に入っている
- [ ] `.env` などの秘密が `deny` に入っている
- [ ] `CLAUDE.md` に、コードを読んでも分からない情報だけが書かれている
- [ ] `CLAUDE.md` が 200 行以内に収まっている
- [ ] `claude` を起動して `/context` を叩き、意図したファイルが読み込まれている
- [ ] `.claude/` と `CLAUDE.md` が git に入っている
- [ ] `CLAUDE.local.md` と `.claude/settings.local.json` が `.gitignore` に入っている

最後の一つを忘れると、自分のローカル設定をチームに配ってしまう。

## 雛形とスキル

[templates/](../templates/README.md) の中身をコピーすれば、上の構成をそのまま持ち込める。

このリポジトリには、立ち上げを対話で進めるスキルも置いてある。
新しいプロジェクトのディレクトリに `.claude/skills/new-project-setup/` をコピーして
`/new-project-setup` と打つと、検証手段から順に聞き取りながら設定を作る
（実装は [.claude/skills/new-project-setup/SKILL.md](../.claude/skills/new-project-setup/SKILL.md)）。
