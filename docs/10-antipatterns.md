# つまずきどころ

うまくいかないときの症状は限られている。原因の見当を先に付けられると、
設定をやみくもに足す前に手が打てる。

| 症状 | よくある原因 | 対処 |
|------|-------------|------|
| 指示が守られない | ファイルが読み込まれていない | `/context` で確認する |
| 途中から指示を忘れる | 文脈が埋まっている | `/clear` するか、調査を分離する |
| 訂正しても直らない | 失敗した方針が文脈に残っている | `/clear` して指示を書き直す |
| 完成したと言うが動かない | 検証手段が無い | テストか実行できる確認手順を渡す |
| 確認ばかりで進まない | 権限の許可が足りない | 繰り返すコマンドを `allow` に入れる |
| スキルが呼ばれない | `description` に状況が書かれていない | いつ使うかを具体的に書く |
| 頼んでいないスキルが動く | 自動呼び出しが有効 | `disable-model-invocation: true` を付ける |
| 調査で毎回文脈が埋まる | 本体で読ませている | サブエージェントに投げる |

## 一つのセッションで何もかもやる

一つの作業を始め、途中で無関係なことを聞き、また元の作業に戻る。文脈が関係ない情報で埋まり、
最初の指示が効かなくなる。

作業を切り替えるときは `/clear` する。ついでの確認なら `/btw` を使えば、
回答が会話履歴に残らない。

## 訂正を積み重ねる

期待と違う結果が出て訂正し、まだ違って訂正し、また訂正する。訂正するたびに、
失敗した方針が文脈に増えていく。エージェントはそれを読み続ける。

二回訂正しても直らないなら、そこで `/clear` する。何がまずかったかを織り込んだ指示を
一度で書き直したほうが、そのまま続けるより速い。

## CLAUDE.md に何もかも書く

規約が守られないので、規約を足す。長くなるので、さらに個々の指示が埋もれる。
この循環に入ると、書けば書くほど守られなくなる。

行数が増えてきたら、足すのではなく減らす。指示なしでも守られるようになった行は消す。
手順として書いた段落は[スキル](04-skills.md)へ、特定のファイルにしか効かない規約は
[パススコープ付きルール](03-rules.md)へ移す。判定が機械にできるものは[フック](06-hooks.md)へ移す。

`/doctor` を実行すると、コードから読み取れる記述を削る候補として出してくれる。

## 指示で強制しようとする

「必ず」「絶対に」と書いても、`CLAUDE.md` は指示文のままである。強調は追従率を上げるが、
保証にはならない。しかも複数の行を強調すると、どれも目立たなくなる。

例外を許さない要求は、機構に移す。整形やテストは `PostToolUse` と `Stop` のフックへ、
触らせないパスは権限ルールの `deny` へ。移した後は `CLAUDE.md` から該当の行を消す。

## 矛盾したまま放置する

上位ディレクトリの `CLAUDE.md`、`.claude/rules/` のファイル、プロジェクトの `CLAUDE.md` に、
違うことが書いてある。これらは互いを上書きせず全部が読み込まれるので、
どちらが採用されるかは決まらない。

規約を変えたときは、同じ話をしている他のファイルも読み直す。モノレポで他のチームの
`CLAUDE.md` まで拾ってしまうなら、`claudeMdExcludes` で除ける。

## 生成された草案をそのまま置く

`/init` の出力は、エージェントがコードを読んで書いたものである。つまり、
エージェントがコードを読めば分かる内容が中心になる。ディレクトリ構成の一覧や依存の列挙は、
毎セッション読み込ませる価値が薄い。

生成後に一度削り、コードを読んでも分からない情報を手で足す。なぜこの構成なのか、
どのコマンドを叩けばよいのか、どこを触ると壊れるか。

## 範囲を決めずに調査させる

「調べて」とだけ頼むと、数百のファイルを読んで文脈を埋め尽くす。
結論が出る頃には、その結論を使う余地が残っていない。

調べる範囲と、何が分かれば終わりかを指定する。あるいはサブエージェントに投げて、
読んだ中身が本体に載らないようにする。

## レビューの指摘を全部直す

指摘を探せと言われたレビュアーは、問題が無くても何かを指摘する。
それが依頼された仕事だからで、指摘の数は品質の指標にならない。

全部に対応すると、要らない抽象化と、起こり得ない場合への防御と、無意味なテストが増える。
レビューを頼むときに、正しさか明示した要件に関わるものだけを挙げるよう指定し、
残りは任意として扱う。

## 権限を締めすぎる

安全側に倒して何も許可しないと、テストのたびに確認が入る。十回目には、
開発者はもう内容を読まずに承認している。危ない操作への注意力は、そこで失われている。

安全だと分かっているものは先に許可する。禁じたいものだけを狭く `deny` に書く。
広い `deny` に例外は書けないので、`Bash(aws *)` のような大きな禁止を置く前に、
本当に禁じたい操作だけを指定できないかを考える。
